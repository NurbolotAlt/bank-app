# Bank App

Pet-проект банковского приложения — backend на Spring Boot + мобильный клиент на Flutter. Делал один, чтобы наконец нормально выучить Java, потому что до этого был чисто C++ и Python бэкграунд.

Это не настоящий банк и не претендует на него — просто хотелось сделать что-то посерьёзнее очередного CRUD-туториала, с реальной денежной логикой, которая не разваливается при первой же попытке её сломать.

## С чего всё началось

Идея была простая: взять что-то похожее на mBank (у нас в Кыргызстане им многие пользуются), но добавить то, чего там нет — например, возможность одолжить денег другому пользователю с процентом и сроком, а не просто голый перевод. Плюс хотелось, чтобы это реально работало как банк изнутри, а не просто таблица `users` с полем `balance`.

## Главное архитектурное решение

У счёта нет поля `balance`. Вообще. Баланс каждый раз считается заново — это сумма всех записей в отдельной таблице `ledger_entries`. Каждая операция (перевод, депозит, вывод) создаёт минимум две такие записи: одну со знаком минус на счёте отправителя, другую со знаком плюс на счёте получателя. В сумме всегда ноль.

Это называется double-entry bookkeeping, и на этом принципе несколько сотен лет держится вся мировая бухгалтерия. Звучит как оверинжиниринг для pet-проекта, но на деле дало кучу плюсов: полная история движения денег, а не просто "текущее число", и что важнее — любую ошибку в коде, где деньги "теряются" или "появляются из ниоткуда", сразу видно, потому что сумма перестаёт сходиться к нулю.

Даже депозит и вывод устроены так же — завёл служебный счёт `EXTERNAL`, который как бы представляет внешний мир. Пополнение — это перевод от `EXTERNAL` к юзеру, вывод — наоборот. Один и тот же код везде, никаких особых случаев.

## Что внутри

- **Java 25 + Spring Boot 4** — бэкенд
- **PostgreSQL + Flyway** — база и миграции
- **JWT** — свой сервис генерации/проверки токенов, свой security filter, без готовых библиотек авторизации
- **Testcontainers** — интеграционные тесты на реальной, а не поднятой в памяти БД
- **Flutter** — мобильный/веб клиент

### Что умеет

- Регистрация автоматически открывает счёт
- Переводы между счетами, депозит, вывод — с идемпотентностью (повторный запрос с тем же ключом не задвоит операцию)
- Простой антифрод: не даст перевести больше 90% баланса за раз и блокирует слишком частые операции подряд
- Нельзя тронуть чужой счёт, даже зная его номер — проверяется реальное владение
- P2P долги — можно одолжить кому-то денег под процент и с датой возврата, погашать можно частями
- В приложении можно смотреть баланс, историю операций, свайпать между несколькими счетами (да, у одного юзера их может быть несколько)

## Пара багов, которые реально нашёл и починил

Расскажу, потому что горжусь именно этим больше, чем самими фичами.

Когда писал интеграционный тест на гонку (два потока одновременно переводят деньги с одного счёта, у которого хватает баланса только на одну операцию) — тест сначала падал вообще не из-за гонки, а с `LazyInitializationException`. Оказалось, что `deposit()` и `withdraw()` вызывали `transfer()` напрямую, внутри одного и того же класса, а Spring реализует `@Transactional` через прокси-обёртку — и вызов "через себя" эту обёртку обходит стороной. Транзакция просто не открывалась. Починил через `@Lazy`-инъекцию сервиса в самого себя.

После этого тест таки дошёл до настоящей проверки — и упал уже по делу: оба перевода проходили одновременно, баланс уходил в минус. Добавил `SELECT ... FOR UPDATE` (пессимистичную блокировку) на счёт-отправитель внутри транзакции, и только тогда тест стал зелёным.

Было приятно поймать это именно тестом, а не случайно на проде — то есть тест реально отработал свою задачу, а не просто числился в проекте для галочки.

## Известные дыры (специально не стал закрывать сейчас)

- Депозит никак не ограничен по сумме и частоте — в реальной системе это была бы дыра для отмывания денег. Для pet-проекта без реальной внешней платёжной интеграции это осознанное упрощение, но я про него помню.
- История операций без пагинации — если накопится много записей, будет тормозить.
- У Flutter-клиента нет нормальной обработки офлайна и retry-логики, только базовый catch с текстом ошибки.

## Как запустить

Backend:
```
docker compose up -d
./gradlew bootRun
```

Тесты (нужен запущенный Docker Desktop, Testcontainers сам поднимет отдельную БД):
```
./gradlew test
```

Flutter-клиент:
```
cd bank_app_flutter
flutter pub get
flutter run
```
Перед запуском поправь `lib/config.dart` под своё окружение — там комментарий, какой адрес для чего использовать (эмулятор Android, десктоп, реальный телефон).

## Что бы сделал по-другому, если начинать заново

Наверное, сразу бы завёл `@Lazy`-паттерн для self-invocation как привычку, а не как то, что нашёл через боль. И, может, стоило раньше начать писать тесты — та гонка с балансом просидела бы в коде до первого реального конкурентного запроса на проде, если бы я не написал тест специально под неё.
